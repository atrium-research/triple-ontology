# Motivating Scenario - Iteration 19

## Name
Profile enrichment

## General Description
The GoTriple Profiles index maintains both author profiles, automatically created from the metadata of harvested documents, and the profiles of registered users of the platform. Up to iteration 18 the ontology models a `triple:Profile` with only a name, exactly one internal identifier and an optional online account. The ADR 005 "GoTriple Data Model revision" (LUMEN WP4/T4.2, Table 3) prescribes a much richer profile: personal names, a self-description, pronouns, a photo, a personal web page, the disciplines the user is interested in, the thesaurus keywords they know about, the languages they speak, their affiliation, a registered-user flag, an open-to-collaboration flag, the date of the last update in the GoTriple index, and a proper management of person persistent identifiers (ORCID, IdRef, ISNI, ResearcherID, the OPERAS/GoTriple id) alongside the internal Elasticsearch identifier.

This iteration extends `triple:Profile` accordingly, reusing FOAF and Schema.org properties wherever a suitable one exists and minting TRIPLE properties only where no consolidated standard property is available (pronouns, registration and collaboration flags). Person PIDs reuse the identifier pattern already in place since iteration 01: each identifier carries a scheme and a literal value, and the scheme alone discriminates its nature. A profile therefore carries several identifiers, and which of them are mandatory is stated in the SHACL shapes rather than in OWL.

## Technical Specification
- Reuse of FOAF properties: `foaf:givenName`, `foaf:familyName` for personal names, `foaf:topic_interest` for the disciplines of interest (chosen by the user or automatically detected from the author's publications), with values from the existing `triple:Discipline` vocabulary.
- Reuse of Schema.org properties: `schema:description` (plain or language-tagged, following the union datatype convention of issue #43), `schema:knowsAbout` with `schema:DefinedTerm` values for thesaurus keywords (the property is natively declared for Person and Organization, so no TRIPLE sub-property is needed here, unlike the creative-work case of iteration 18), `schema:knowsLanguage` with `schema:Language` values, `schema:affiliation` with `foaf:Organization` values, `schema:image` for the profile photo URL, `schema:url` for personal web pages, `schema:dateModified` for the last GoTriple update (date pattern: `xsd:date`, at most one).
- New TRIPLE datatype properties where no standard property is consolidated: `triple:pronouns` (`xsd:string`), `triple:registeredUser` (`xsd:boolean`), `triple:openToCollaboration` (`xsd:boolean`).
- Identifiers via the existing DataCite pattern, with three distinct fields of Table 3 kept apart by their scheme: the internal Elasticsearch `id` uses `triple:internal_id_schema`, the `pid` minted by GoTriple uses `datacite:ark`, and the `goTripleId` uses the new `triple:gotriple_id_schema`.
- External person PIDs (the `user_identifier` field: ORCID, IdRef, ISNI) are, like every other identifier, plain `datacite:Identifier` instances distinguished by their scheme. The ontology has no identifier subclasses at all: the scheme is the kind.
- The `PID_Type` requirement of the ADR is satisfied by the scheme individuals rather than by a separate SKOS vocabulary, consistently with how every other identifier scheme is modelled in the ontology: reused from the DataCite ontology (`datacite:orcid`, `datacite:isni`, `datacite:researcherid`) and minted in the TRIPLE namespace only where DataCite has none (`triple:idref_schema`, `triple:gotriple_id_schema`).
- Which identifiers a profile must carry is expressed in `shapes/entity.shapes.ttl`, not as an OWL axiom: `tsh:ProfileIdentifiersShape` requires exactly one internal id and exactly one ARK PID, and no original identifier — a registered user is created inside GoTriple and comes from no source system.
- The `author_of` field is not materialized as a property: the documents attributed to a profile are retrieved as the inverse of `schema:author` (decision recorded in issue #44).
- Out of scope, per ADR 005 and issue #44: `hasOccupation` (its controlled vocabulary is not yet defined — deferred to a dedicated issue), `numberOfDocuments` and cluster counters (computed by the platform), the struck-through fields `aka` and `currentRole`.
- Compatibility: extends the `triple:Profile` class of iteration 06; the `skos:exactMatch foaf:Agent` alignment of iteration 16 is left untouched (issue #30 is still under discussion).

## Examples
- Example 1: Sofia Rossi is a registered GoTriple user with a complete profile: given name "Sofia", family name "Rossi", an English self-description, pronouns "she/her", a profile photo, a personal web page, two disciplines of interest (Cultural heritage and museology; Methods and statistics), the thesaurus keyword "Distant reading", two known languages (Italian, English), an affiliation to the University of Bologna, `registeredUser` true, `openToCollaboration` true, a last GoTriple update on 2026-06-15, and five identifiers: the internal Elasticsearch id, the persistent identifier minted by GoTriple, an ORCID, an OPERAS/GoTriple id and an IdRef id.
- Example 2: João Almeida is an author profile automatically created from harvested document metadata, not associated with a registered user: a full name, `registeredUser` false, the internal Elasticsearch id, the ARK PID that GoTriple mints for every profile, and an ISNI extracted from the provider metadata.
- Example 3: the document "Mapping early modern correspondence networks with distant reading methods" is authored by both Sofia Rossi and João Almeida; the documents a profile is author of are retrieved through the inverse of `schema:author`.
